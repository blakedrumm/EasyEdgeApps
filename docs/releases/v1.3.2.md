# Easy Edge Apps 1.3.2

Author: Blake Drumm (blakedrumm@microsoft.com)

Optional independent fresh sessions for each saved website, available in the portable manager and per-user MSI.

## What's new

- Select a website, check **Fresh session each time**, save, and approve. New websites and existing normal websites remain unchanged unless opted in.
- Each launch uses a new empty Edge profile. Cookies, cache, local storage, and other site data are removed after that session's browser process tree ends. Separate launches do not share state or interrupt each other.
- Normal Edge data and downloaded files are not cleared. Sign-ins and site preferences usually need repeating; Windows/site single sign-on can still authenticate independently.
- A small locally compiled Windows executable manages each fresh session without PowerShell, a console, service, or scheduled task. Ordinary shortcuts still launch Edge directly.
- Install accepts `-SessionMode Fresh` and `-SessionMode Normal`. Omission preserves the saved choice. App Kit schema 2 carries the choice without carrying executables, paths, profiles, or browser data; protected kits retain the existing encrypted envelope.
- Check and Repair recognizes missing/outdated owned launchers. Changed executables, damaged metadata, and conflicting files fail closed; no normal-profile fallback is requested.

## Cleanup and compatibility

Close all related windows and browser processes for the session. Cleanup handles long Edge paths and briefly retries file locks. A crash, power loss, permissions problem, or persistent lock can leave marked data on disk; it is never reused, and a later fresh launch retries cleanup. Resolve cleanup warnings before disabling or removing the website. This is not secure erasure, anonymity, a kiosk, or deletion of downloaded files and server-side records.

Fresh launches require a non-elevated Windows session. Saving/importing/repairing fresh websites requires the Windows .NET Framework compiler. A policy overriding Edge's UserDataDir blocks launch, and organization application controls may block the executable. No security controls or policies are bypassed.

After changing modes, unpin the old taskbar entry and pin the current saved shortcut again. Directly pinning an Edge window can bypass the fresh launcher. Windows owns pin creation and grouping; verify the actual pinned launch on the intended computer.

Fresh websites and schema-2 kits require 1.3.2 or later; older versions reject them. Schema-1 imports preserve an existing destination's fresh choice. All-normal exports stay schema 1. MSI maintenance preserves website data and does not rebuild per-website launchers; use Check and Repair when needed after an update.

## Download and upgrade

Close setup and run **EasyEdgeApps-1.3.2-x64.msi** in the same Windows account, or replace the portable **EasyEdgeApps.ps1**. Existing websites and preferences remain compatible. Automatic update checks and debug logging remain off by default.

The script, MSI, and launchers are unsigned. Obtain downloads from this release and compare them with **SHA256SUMS.txt**. The matching **WiX-5.0.2-source.zip** and complete license notices remain included. Checksums do not authenticate publisher identity. Encrypted App Kit exports remain experimental pending independent security review.

## Verification

Fourteen isolated application suites run on Windows PowerShell 5.1 and PowerShell 7. Session regressions cover continuous allocation leases, child-tree lifetime, interruption, long paths, file locks, junctions, exact ownership markers, metadata/executable tampering, compiler failure, transactional rollback, CLI options, kit portability, consent, stale saves, and 12/18/24-point GUI layouts within 1024 by 768. MSI lifecycle and compiled manager-launcher checks remain release and CI gates.

A separate local test with Edge 152.0.4191.66 verifies three real app windows against a synthetic loopback site: empty cookie/storage state, independent cache requests, closing one while another remains open, a clean relaunch, and profile removal. It does not use debugging flags or modify normal profiles.

Live managed-policy/elevated rejection, final taskbar pin behavior, real-site sign-in, physical accessibility/high-DPI layouts, and cross-computer handoff still need acceptance checks on the intended computer. See the README and Security document for the full boundaries.
